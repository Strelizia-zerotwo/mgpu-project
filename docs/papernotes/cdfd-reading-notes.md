# CDFD：以复制为中心的多 GPU 内存管理——阅读笔记

> 核心思想：数据可以粗粒度搬运，但不必粗粒度地一直保留。先通过批量复制降低传输和页面管理开销，再根据实际使用情况撤销不划算的小块副本。


<a id="paper-overview"></a>

## 1. 论文整体概括

### 1.1 一段话概括

CDFD 针对细粒度多 GPU 页面迁移与复制中带宽利用不足、页面管理开销较高的问题，提出“先粗粒度复制、后细粒度去重”。它先以 32 MB 粒度复制数据，保留源端副本并改善本地访问；随后根据子页的本地访问收益与远端更新成本，以 2 MB 或 64 KB 粒度撤销不划算的副本。同时，通过动态复制率控制副本的显存占用，避免过度挤占常规页。作者增加副本位置跟踪、访问统计和复制／去重管理支持，在 MGPUSim 仿真中相对 GPS 和 GRIT 分别获得 66% 和 65% 的平均性能提升。

### 1.2 问题与设计的因果关系

```text
细粒度迁移／复制频繁
    → 小消息带宽利用不足
    → 缺页、冲刷、TLB 失效等管理开销重复发生
    → 改用粗粒度复制

粗粒度复制包含不必要的数据
    → 多占显存
    → 不必要的副本仍需接收写更新
    → 用细粒度去重撤销低收益副本

复制页与常规页争夺显存
    → 用动态复制率调节副本空间预算
```

### 1.3 为什么选择复制，而不只是迁移

假设一个 2 MB 页位于 GPU A，GPU B 只需要其中的 64 KB，而 A 仍频繁访问其他部分。

- **迁移整页到 B：**B 的访问变成本地，但 A 对该页的访问变成远端，新增远端访问可能更多。
- **复制整页到 B：**A 保留数据，两边都能本地读；代价是额外容量占用，以及后续副本更新。

因此，本文同时处理两个问题：用复制避免粗粒度迁移破坏源端局部性，用细粒度去重控制粗粒度复制的副作用。

## 2. 阅读中涉及的基础知识

### 2.1 NUMA：访问不同位置的内存，性能不同

NUMA 是 **Non-Uniform Memory Access，非均匀内存访问**。中文译本中的“非一致性内存访问”容易与数据一致性混淆。

```text
GPU A ── 本地显存 A
  │
NVLink
  │
GPU B ── 本地显存 B
```

对 A 而言，访问 A 的显存通常延迟低、带宽高；访问 B 的显存需要经过互连，通常延迟更高、可用带宽更低。对 B 而言则相反。

**NUMA 描述访问性能的差异，缓存一致性描述多个副本如何保持正确，两者不是同一个概念。**

### 2.2 不同 GPU 运行不同 kernel，为什么还能统一寻址

这三个问题彼此独立：

| 概念 | 回答的问题 |
| --- | --- |
| kernel 启动与调度 | 代码在哪块 GPU 上执行？ |
| 虚拟地址空间 | 指针表示哪个逻辑内存对象？ |
| 物理内存位置 | 数据实际放在哪块 GPU 或主机内存？ |

一次普通 CUDA kernel 启动只发生在选定的一块 GPU 上。同一进程仍可以向不同 GPU 的 kernel 传入同一个托管内存指针，由统一内存机制协调映射和数据驻留。并发读写需要正确同步。

- **UVA，统一虚拟寻址：**统一地址布局，但不自动保证其他 GPU 能访问任意指针。
- **UVM／Unified Memory：**进一步管理页面映射、驻留、迁移等。
- 统一虚拟地址空间不要求所有 GPU 共用一张物理页表；本文中各 GPU 有自己的本地页表和 GMMU。
- 不同进程不会因为使用多 GPU 就自动共享地址空间。

### 2.3 TLB、页表、GMMU 和远端缺页

| 名称 | 作用 |
| --- | --- |
| 页表 | 保存虚拟页到物理页的映射及相关属性 |
| PTE | Page Table Entry，页表中的一条记录 |
| TLB | 缓存常用地址映射，减少页表遍历 |
| GMMU | GPU 内存管理单元，参与地址转换等工作 |
| far-fault | 本文模型中，本地转换无法完成，需要主机 UVM 驱动处理的远端缺页 |

```text
GPU A 访问虚拟地址
    → 查各级 TLB
    → 未命中后由 GMMU 查本地页表
    → 仍无法完成转换，触发 far-fault
    → 主机 UVM 驱动处理驻留、映射或页面移动
    → 访问恢复
```

需要区分：

- **TLB 未命中不一定缺页：**页表中可能已有有效映射。
- **远端访问不一定缺页：**已有有效远程映射就可以直接访问。
- **缺页不意味着数据不存在：**数据可能在其他 GPU 或 CPU 内存里，不一定涉及磁盘。

### 2.4 CPU 如何知道页面在哪块 GPU

UVM 管理页面的分配、迁移与复制，并维护驻留位置等元数据。例如：

| 虚拟页 | 驻留位置 | 对应物理位置 |
| --- | --- | --- |
| P | GPU 1 | 物理页 35 |
| Q | GPU 0 | 物理页 82 |
| R | 主机内存 | 主机物理页 120 |

缺页时，驱动根据进程／地址空间及虚拟地址定位相应记录。页面迁移或复制后，相关记录随之更新。

**会查询主机内存中的管理结构，但不会扫描全部主机内存或所有 GPU 显存来搜索数据。**驻留集合等信息也可以放在页表之外的结构中，不必全塞进一个 PTE。

### 2.5 MSHR：记录尚未完成的未命中

MSHR 是 **Miss Status Holding Register，未命中状态保持寄存器**。

以 TLB MSHR 为例：

```text
线程 A 查询页 P，TLB 未命中
    → 登记 MSHR，向下一级请求转换

结果未返回，线程 B 也查询 P
    → 发现 P 已经在处理中
    → 合并请求，避免重复发出相同转换

结果返回
    → 填入 TLB，唤醒等待者，释放 MSHR 表项
```

TLB 保存已经得到的结果，MSHR 跟踪正在等待的结果。MSHR 满时，无法合并的新未命中通常需要等待。数据缓存也有 MSHR，只是跟踪对象变成缓存行。

### 2.6 MMU 开销与冲刷在飞指令

广义的地址转换和页面管理开销包括：

- TLB 查询、页表遍历、转换请求排队。
- 缺页处理、页表更新、TLB 失效。
- 为页面迁移／复制协调在途访问、处理缓存等。

其中一部分由 UVM 驱动与运行时承担，不能全算作 MMU 硬件独立执行的操作。

**在飞指令**是已经进入执行流程、但尚未完成的指令。例如，一次写已经发出，却还在内存系统中等待。

迁移／复制前需要处理这些访问，原因包括：

1. 防止复制期间仍有写入，导致新副本漏掉更新。
2. 防止已拿到旧物理地址的请求在映射改变后继续访问旧位置。
3. 与缓存脏数据、旧 TLB 映射的处理建立正确顺序。

“冲刷”不意味着整个 kernel 从头运行。具体等待排空还是取消并重放部分请求，论文的概述没有展开。

### 2.7 缺少跨 GPU 缓存一致性，为什么还能复制页面

如果 A 随意缓存了 B 的数据，而 B 修改后不通知 A，A 就可能继续命中旧值。因此，本文所讨论的系统不允许请求方无管理地保留远端数据并反复命中。

**不在请求方缓存，不等于任何缓存都不能服务请求。**数据可能来自远端 GPU 的缓存，但传输仍要经过互连。

页面复制能够工作，是因为增加了副本协议：

| 方案 | 写入时如何处理 |
| --- | --- |
| 传统只读页复制 | 读时允许多副本；写入触发管理操作，撤销其他副本及旧映射 |
| GPS／CDFD 的更新式复制 | 跟踪副本持有者，传播普通写更新，并专门处理同步与系统域操作 |

复制机制不等于商用 GPU 默认具有自动、完整的跨设备缓存一致性协议。

### 2.8 弱访问、强访问、作用域与系统域

内存模型规定：其他线程可以按什么顺序观察到访问，以及一次读允许返回什么结果。

| 术语 | 概念理解 |
| --- | --- |
| 弱访问 | 普通读写本身不承担跨设备发布／获取的同步职责 |
| 强访问 | 带有相应语义与作用域，按限定提供保证；不代表全局严格有序 |
| 作用域 | 同步保证覆盖的参与者范围 |
| GPU 域 | 覆盖同一 GPU 范围内的相关参与者 |
| 系统域 | 能覆盖不同 GPU 和 CPU 等参与者，具体取决于平台及内存支持 |
| fence，栅栏 | 约束相关内存操作的顺序，通常不独立承担通知或等待对方的职责 |

例如，A 写数据后设置标志，B 看到标志后读数据：

```text
A：写 data
   用系统域 release 语义发布 ready

B：用系统域 acquire 语义读取 ready
   接收到对应发布后，再读取 data
```

在访问受支持、同步匹配且无其他冲突写入的前提下，这种协议才能建立需要的顺序与可见性。普通读写标志不是可靠的同步替代品。

**没有建立同步，不表示永远看不到更新，而是不能依赖期望的时间和顺序。系统域也不表示让所有 GPU 停下来等待。**

CDFD 对系统域写另作处理：访问复制页时触发缺页，协调在途访问，使副本收敛为单一权威版本，再将访问指向该版本。见中文译本第 10 页 IV-D。

### 2.9 内存足迹、工作集与冷页面

| 概念 | 含义 |
| --- | --- |
| 整体内存足迹 | 应用整体占用的内存 |
| 工作集 | 某个时间窗口内访问的数据集合，随时间窗口和程序阶段变化 |
| 冷页面 | 最近较少使用或较长时间未使用的页面，是对当前活跃程度的描述 |
| LRU | Least Recently Used，依据最近访问情况选择淘汰候选 |

一个程序可能占用 40 GB，但当前阶段只活跃访问 3 GB。这不代表其他 37 GB 无效，也不代表可直接覆盖。

“复制利用未用内存而不干扰工作集”的目标是：优先使用空闲空间，或在必要时腾出较冷页面，尽量不挤走当前活跃数据。复制仍会占用带宽等资源，不是零成本。

**工作集小不等于空闲显存多。**若显存已经满了，冷页面中的有效数据仍需要按规则保留或迁移。

### 2.10 LRU 表头、表项与采样粒度

LRU 可概念化为：

```text
较久没访问                           最近刚访问
A ───── B ───── C ───── D ───── E
```

再次访问 A 后，它会被更新到最近访问的一端。实际实现可能使用近似 LRU，不必为每次访问维护完全精确的全局顺序。

论文说扫描 LRU 列表前几千个表项。结合其“样本中复制页多则降低复制预算”的逻辑，应理解为扫描偏向淘汰候选的部分。**不能据此给所有 LRU 实现下结论：表头永远是冷页面。**

论文没有明确说明：

- 一个 LRU 表项本身占多少字节。
- 一个 LRU 节点对应多大的页面／管理区域。
- 页面大小不一致时，采样按节点数量还是字节数加权。

表项只是管理记录，不存整页数据；32 MB 复制粒度也不能直接当成 LRU 节点粒度。

### 2.11 NCCL 的五种集合通信

NCCL 是 NVIDIA Collective Communications Library，多 GPU 通信库。本文列出五种常见集合通信，并不表示 NCCL 只有这五种功能。

| 原语 | 含义 | 两块 GPU 的简单例子 |
| --- | --- | --- |
| Broadcast | 一份数据分发给其他 GPU | A 的 `[1,2]` 发给 B，A 保留原数据 |
| Reduce | 多份数据规约，结果给指定 GPU | `[1,2] + [10,20] → A 得到 [11,22]` |
| AllReduce | 规约结果每块 GPU 都拿到 | A、B 都得到 `[11,22]` |
| AllGather | 拼接各 GPU 数据，完整集合每块都拿到 | A、B 都得到 `[1,2,10,20]` |
| ReduceScatter | 规约后各 GPU 拿一部分 | A 得到 `[11]`，B 得到 `[22]` |

AllGather 是拼接，不是求和。从结果上看，ReduceScatter 后接 AllGather 可以完成 AllReduce，具体实现由库选择。

### 2.12 广播延迟与 NVSwitch 调度

向 7 块 GPU 广播，不等于源 GPU 串行执行 7 次完整复制。通信库可组织并行传输、转发和流水线；具体使用哪种算法，要看实际配置，不能只根据最终延迟反推。

论文在 NVLink 3.0 测试中观察到，7 块接收 GPU 相对单块接收的平均延迟只增加 13.27%。这是特定平台与测试条件下的观察，不是普遍常数。

NVSwitch 的物理链路保持连接，交换机内部仍需根据目标转发数据：

- 不同流量使用不同出口，可以并行。
- 多个请求争用同一出口，可能需要仲裁、排队。

**“全互通”不等于无限带宽，也不等于任意访问模式都无竞争。**

## 3. CDFD 的机制与硬件结构

### 3.1 三种复制率：控制副本空间预算

| 指标 | 定义／含义 | 作用 |
| --- | --- | --- |
| 当前复制率 | 本 GPU 复制页总大小 ÷ 本 GPU 显存容量 | 记录实际占用 |
| 目标复制率 | 运行时希望副本占用的空间比例 | 指导空间分配，是可调整目标 |
| 采样复制率 | LRU 采样部分中复制页的占比 | 估计副本在冷页面中的相对占比，帮助调整目标 |

例如，80 GB 显存中有 16 GB 复制页，当前复制率为 20%。目标为 30% 时，可理解为当前希望给副本约 24 GB 的空间预算，不是硬划分出一块只能存副本的显存。

论文采用的反馈规则：

```text
采样复制率 > 目标复制率
    → 副本在较冷页面中占比偏高
    → 下调目标复制率

采样复制率 < 目标复制率
    → 相对而言副本更值得保留
    → 上调目标复制率
```

当显存空间紧张时，当前／预计复制后的副本占比与目标共同指导选择：优先减少副本，还是逐出较冷的常规页以容纳新页面。

**复制率管理“留多少副本”，子页统计管理“具体删哪些副本”。**

### 3.2 先以 32 MB 粒度复制

面对合适的远端读缺页，运行时考虑把包含所需数据的 32 MB 区域复制到请求方。目的是摊销管理开销、提高传输效率，同时保留源端数据。

32 MB 是本文选定的设计参数，与其采用的 TLB 覆盖组织有关，不是所有平台上恒定最优的传输大小。

### 3.3 再以 2 MB 或 64 KB 粒度去重

一个 32 MB 区域可先按 16 个 2 MB 子页观察：

```text
GPU B：[0][1][2][3]……[15]
GPU A：[0][1][2][3]……[15]  ← 完整副本

发现 A 很少用子页 2，却频繁收到它的更新
    → 撤销 A 上的子页 2

GPU B：[0][1][2 ][3]……[15]
GPU A：[0][1][空][3]……[15]
```

结果是释放 A 的容量并停止维护这个副本，代价是 A 再访问子页 2 时需要远端访问。其他保留子页仍然本地可用。

当一个 32 MB 区域去重超过一半，论文将其进一步拆分为 1 MB 管理区域，并在后续按 64 KB 子页去重。

**这里的去重是撤销已知冗余副本，不是内容哈希去重，也不必为了删除冗余副本再把整页搬回去。**相关页表、共享表、TLB 和同步处理仍然有成本。

### 3.4 子页的收益指标

```text
收益指标 = 本地访问次数 - 收到的远端更新次数
```

| 子页 | 本地访问 | 收到的远端更新 | 指标 | 倾向 |
| --- | ---: | ---: | ---: | --- |
| P0 | 100 | 5 | 95 | 保留 |
| P1 | 3 | 60 | -57 | 优先去重 |
| P2 | 40 | 10 | 30 | 相对更值得保留 |

**远端更新**是其他 GPU 修改共享数据后发给本地副本的更新；它不是本 GPU 去远端读取的次数。本地已有副本，仍然可能频繁接收这种更新。

这个减法是排序候选的简化指标，不表示两类操作耗时或能耗完全相等。

### 3.5 复制 TLB 与显存中的共享表

这里并非两个 TLB，而是两级副本位置记录：

| 结构 | 保存内容 |
| --- | --- |
| 显存中的复制页共享表 | 按 VPN 索引，记录其他副本的物理位置 |
| 复制 TLB | 在片上缓存近期常用的副本位置记录 |

```text
写入复制页 P
    → 查复制 TLB
        → 命中：直接得到其他副本位置
        → 未命中：查询显存中的共享表，并填入复制 TLB
    → 通过 GMMU 向对应 GPU 发出远端更新
```

表放在 GPU 自己的显存中仍然有用：本地记录可以描述远端位置。页复制和去重时，需要更新相关 GPU 的位置记录，避免继续更新已经撤销的副本。

### 3.6 DDU、CDB 与访问计数监视器

| 结构 | 全称 | 职责 |
| --- | --- | --- |
| DDU | Duplication and Deduplication Unit | 综合空间预算与候选统计，协调复制／去重及相关运行时操作 |
| CDB | Candidate Deduplication Buffer | DDU 内部的候选表，记录候选区域及子页的访问和更新统计 |
| 访问计数监视器 | Access Count Monitor | 统计被监视页面的本地访问，周期性同步给 CDB |

```text
其他 GPU 的更新 ───────────────→ CDB 更新远端计数
本地访问 → 访问计数监视器 ─────→ CDB 更新本地计数
                                      ↓
                        DDU 需要去重时选择低收益子页
```

CDB 容量有限，重点跟踪频繁接收远端更新的复制页；表满时，淘汰远端更新总数较少的候选记录。它用子表项分别跟踪大区域中的小页，支持局部去重。

监视信息按周期更新，论文采用右移旧计数并结合新计数的方式，让旧历史逐渐衰减。因此，统计不是永不衰减的终身累计。

**CDB 逐出记录 ≠ 数据副本去重。**前者只是停止跟踪候选，后者才实际释放显存。DDU 也不是独立完成全部数据搬运的 DMA；它需要与 UVM 运行时等组件协作。

## 4. 关键实验结果与阅读注意事项

### 4.1 分清真实测量、仿真与成本估计

| 证据 | 方法 | 能支持的结论 |
| --- | --- | --- |
| NVLink 3.0／4.0 通信特性 | A100／H100 平台实测 | 指定平台、传输路径和负载下的行为 |
| UVM 迁移成本 | `cudaMemPrefetchAsync()` 与同步构成的微基准 | 纳入软件与 MMU 管理路径后的迁移特性 |
| CDFD 端到端性能 | 修改后的 MGPUSim | 仿真配置与工作负载下的相对性能 |
| 面积、能耗等 | 存储统计和模型估算 | 设计成本的估计，不等同于制造后的芯片实测 |

主评估为 4 GPU，每 GPU 2 GB 显存，使用 13 个基准；另有 GPU 数量、内存足迹和 NVLink 代际等敏感性研究。

### 4.2 不要把全部收益归给细粒度去重

| 对比 | 论文报告的平均提升 |
| --- | ---: |
| CDFD 相对 GPS | 66% |
| CDFD 相对 GRIT | 65% |
| CDFD 相对只做粗粒度复制的 CoarseDup | 约 8% |
| 3 倍内存足迹下，CDFD 相对 CoarseDup | 21% |

论文指出，主要收益来自粗粒度复制降低传输频率与管理开销。细粒度去重和动态空间管理进一步改善容量占用、更新成本以及内存压力下的表现。

**66% 性能提升约为 1.66 倍性能，不是执行时间降低 66%。**在工作量一致时，时间约为原来的 `1 / 1.66 ≈ 60.2%`，即减少约 39.8%。

### 4.3 工作集小，不等于有相同比例的空闲容量

图 9 中，100 ms 窗口内访问过的本地 GPU 内存平均约占本地物理内存的 11%。分母不是应用整体内存足迹。

它支持“短期活跃区域较小”，但不能直接推出其余 89% 可覆盖，也不能保证下一阶段不会访问那些页面。

### 4.4 带宽结论要绑定测试路径

NCCL 集合通信耗时、UVM 迁移耗时与裸链路传输延迟不是同一个量。消息大小、软件提交、通信算法、GPU 数量和拓扑都会影响测量。

作者增加 UVM 微基准，使动机不只依赖 NCCL，但“4 KB 与 32 MB 延迟相近”“争用可以忽略”仍应绑定本文测试条件。

结合 ParallelKittens 的阅读经验，还应追问：换用更高效的小粒度设备端传输后，页面管理路径的最佳粒度是否变化。不能把不同机制的结果直接混用。

### 4.5 容量很小，不代表所有硬件成本都很小

论文估计每 GPU 新增片上存储为 12,800 B，并估计额外逻辑和功耗。这说明存储规模有限，但仍需关注端口数、匹配逻辑、更新吞吐、时序、布线与软件开销。

这个数值不是所有片上／片外元数据和运行时成本的总和。

### 4.6 正确性协议不能省略

CDFD 不只是两个搬运 API。复现还需要副本更新、映射变更、缓存和 TLB 处理、在途访问协调以及系统域操作支持。

迁移／复制次数减少超过 99% 或某类开销下降 92% 等局部指标，也不能直接解释为整个程序同比加速；必须看端到端结果及指标定义。

## 5. 可以借鉴的研究思想

### 5.1 分离传输粒度和保留粒度

大块搬运适合摊销固定成本，小块管理适合精确控制容量。可以将这两种粒度解耦：一次搬来较多数据，再只保留有价值的部分。

可借鉴到预取、缓存填充、分层内存、数据分发等场景。

### 5.2 先做粗决策，再根据运行时行为修正

精确预测每个子页是否有用可能很贵。CDFD 先复制，再观察真实访问与更新，撤销错误选择。

前提是初始试错成本可接受，纠正及时且不昂贵。若粗复制本身造成严重拥塞或挤掉活跃数据，这个思路也可能失效。

### 5.3 不只最小化字节数，还要最小化操作次数

可以用概念模型理解：

```text
总成本 ≈ 操作次数 × 单次固定管理开销
       + 数据传输成本
       + 副本更新成本
       + 容量竞争代价
```

这是解释思路的模型，不是论文的精确公式。多传一些字节、少执行很多次管理操作，可能更快。

### 5.4 全局预算与局部选择分工

复制率解决“副本总共留多少”，子页统计解决“哪些副本值得留”。这种分层决策适合资源预算与对象选择同时存在的问题。

### 5.5 副本价值必须减去维护成本

只看访问热度不够。共享可变数据还要考虑更新流量、失效频率、同步与容量代价。

相同读取次数的两个副本，若一个几乎不更新，另一个频繁被写，保留价值可能完全不同。

### 5.6 用消融实验判断真正的收益来源

将完整方案与“仅粗粒度复制”比较，才能区分基础策略收益与附加硬件、反馈机制的收益。还应在不同内存压力下观察增量价值，而不只报告相对较弱基线的最大数字。
